# 회송리스트 자동화 앱 — 설계 (v2.0)

작성일: 2026-08-26
근거 문서: `구현방안_회송리스트자동화앱.md`(v0.1 draft), `design_mockup.html`(UI 색상/스타일 레퍼런스), 실제 스프레드시트(`XRG1 회송리스트`) 구조 확인, 센터 현장 의견 및 사용자 확인 답변(본 대화)

v1.0 대비 변경: 센터 현장 피드백을 반영해 **작업 흐름을 스캔 우선(조회 → 작업 선택) 방식으로 전면 변경**하고, 실제 스프레드시트 컬럼 구조에 맞춰 데이터 모델과 API를 다시 확정했다. 차량 정보 입력을 폐기·회송 모두에서 제거했다.

## 1. 확정된 결정 사항

### 1-1. 작업 흐름 (센터 피드백 반영, v0.1에서 전면 변경)

- 기존(v0.1): 홈에서 [폐기]/[회송]/[조회] 중 하나를 먼저 선택 → 각 화면에서 다건 스캔 → 리스트 일괄 완료
- **변경(확정)**: 스캔이 곧 시작점이다. 다건 리스트 누적 방식은 사용하지 않고, **건별로 스캔→조회→처리를 완결**한다.
  1. 로그인 후 곧바로 스캔 대기 화면(=조회 화면 겸 홈)에 진입한다.
  2. IPR바코드를 스캔하면 즉시 조회 결과 카드(상품바코드, 오류신고일, 벤더명, 수량, 회수구분, D+6초과여부)와 함께 **[폐기 처리]/[회송 처리]** 버튼이 표시된다.
  3. **[회송 처리]** 선택 시 "회송 방식 선택" 화면에서 [업체직접회수]/[택배]를 **작업자가 직접 선택**한다. (v2.1에서 변경 — 최초에는 조회 결과의 회수구분(M열) 값으로 자동 분기했으나, 현장 피드백에 따라 수동 선택으로 바꿨다. M열 값은 여전히 조회 카드에 참고용으로 표시된다.)
  4. 각 처리(폐기/업체회송/택배회송)는 해당 건 하나에 대해서만 진행하고, 완료되면 **다시 스캔 대기 화면으로 복귀**한다. 다음 상품은 새로 스캔해서 동일한 사이클을 반복한다.
  5. 폐기 처리에서 "폐기존 이동 후 사진"은 **건별로, 폐기 처리 확정 후(현장에서 실제로 폐기존으로 이동한 뒤) 촬영**한다. 촬영 후 처리가 최종 완료되고 스캔 대기 화면으로 돌아간다.
- 이 변경으로 v0.1에 있던 "스캔 리스트 누적 + 개별 삭제" UI는 필요 없어진다.

### 1-2. 항목 변경 (센터 피드백)

- 폐기 처리: 차량번호/접안시간/발차시간 입력 **삭제**. '폐기차량 사진' → **'폐기존 이동 후 사진'** 으로 명칭 변경, 건별·처리 후 촬영으로 시점 변경(1-1 참고).
- 회송 처리(업체·택배 공통): 차량 정보 입력 **삭제**(도크에서 별도 취합).

### 1-3. 중복 IPR바코드 처리

F열(IPR)은 원칙적으로 유일해야 하는 값이다. `inquiry` 조회 시 F열에서 동일 값이 2행 이상 매칭되면 처리를 진행하지 않고 **"중복 IPR바코드 감지"** 경고를 표시하고 처리 화면으로 진입시키지 않는다(어느 행을 대상으로 할지 앱이 임의로 판단하지 않음).

### 1-4. 이미 처리된 건 재처리 방지

조회 시 T열(최종 처리)에 이미 값이 있으면 "이미 처리된 건입니다"를 함께 표시한다. 재처리 자체를 막지는 않되(현장 정정 필요 상황 대비), 경고 후 작업자가 계속 진행할지 확인하게 한다.

## 2. 아키텍처 (v1.0과 동일, 변경 없음)

- **프론트엔드**: PWA 단일 코드베이스 (Vanilla JS, 빌드 도구 없음). `design_mockup.html`의 색상 토큰·스타일을 재사용하되 화면 구조는 2-1의 새 흐름에 맞게 다시 구성한다.
- **바코드 스캔**: 카메라는 `BarcodeDetector` 우선 + `ZXing-js` 폴백. PDA는 포커스 유지 입력창 + `input`/Enter(`keydown`) 감지(XRG1 IPR 스캐너 HID 모드 지원 확인됨).
- **백엔드**: Google Apps Script `doPost(e)`, `Content-Type: text/plain;charset=utf-8` + `JSON.parse(e.postData.contents)`.
- **인증**: 서버측 토큰 검증 없음. 로그인 입력(작업자명, VF ID)은 클라이언트에 세션 보관 후 매 처리 요청에 `worker`로 동봉.
- **사진**: 클라이언트에서 리사이즈(긴 변 1280px) 후 base64 전송, `DriveApp` 저장 후 URL을 로그 시트에 기록.
- **일반 Gmail 계정** 기준 Apps Script 할당량(URL Fetch 20,000회/일, 트리거 90분/일) 적용 — 단일 센터 규모에서는 충분.

## 4. 화면 구성

1. **로그인**: 작업자명 · VF ID 입력 → [시작하기]
2. **스캔 대기(홈 겸 조회)**: IPR바코드 스캔 대기 상태. 스캔 시 `inquiry` 호출 →
   - 미등록: "미등록 IPR바코드" 안내, 계속 스캔 대기
   - 중복 매칭: "중복 IPR바코드 감지" 안내, 처리 화면 진입 차단
   - 정상: 결과 카드(상품바코드/상품명/오류신고일/벤더명/수량/회수구분/D+6초과여부, 이미 처리됨이면 경고 배지) + [폐기 처리]/[회송 처리] 버튼
3. **폐기 처리**: [폐기 처리] 선택 → "폐기존 이동 후 사진" 촬영 화면 → 촬영 완료 시 `processDiscard` 호출(해당 IPR 1건) → 완료 토스트 → 스캔 대기로 복귀
4. **회송 처리**: [회송 처리] 선택 → "회송 방식 선택" 화면([업체직접회수]/[택배] 버튼, 작업자가 직접 선택 — v2.1에서 M열 자동 분기 대신 수동 선택으로 변경)
   - 업체직접회수: 처리 확인 화면(요약 표시 + [처리 완료]) → `processReturnVendor` 호출 → 스캔 대기로 복귀
   - 택배: "운송장번호 스캔" 화면 → 스캔 시 `processReturnParcel` 호출(IPR+운송장 1쌍) → 스캔 대기로 복귀

상단 'XRG1 IPR 스캐너' 타이틀, 우측 상단 홈/로그아웃, 하단 '롯데글로벌로지스' 워터마크는 기존과 동일하게 유지한다. `design_mockup.html`의 색상 토큰(Lotte Red/Navy/Paper, 폐기=Amber, 회송=Blue, 조회=Teal)과 "IPR SCAN LOG" 스캐너 LCD 스타일 패널을 그대로 재사용한다.

## 5. API (Apps Script `doPost`, action 기반 라우팅)

모든 처리 액션은 **건당 1회 호출**(배열 대신 단일 IPR바코드). `token` 필드 없음.

**inquiry** — 스캔 시마다 호출(구 v0.1의 `iprBarcodeLookup`+`inquiry` 통합)
```
요청: { "action": "inquiry", "iprBarcode": "IPR2308050112" }
응답: {
  success: true,
  found: true,
  duplicate: false,
  alreadyProcessed: false,
  iprBarcode, productBarcode, productName,
  reportDate,      // A열
  vendor,          // H열
  qty,             // K열
  method,          // M열: "택배" | "업체직접회수"
  isOverDPlus6,    // R열 값 그대로
  existingStatus   // T열에 값이 있으면 그 값(alreadyProcessed=true일 때)
}
```

**processDiscard**
```
요청: { "action": "processDiscard", "iprBarcode": "...", "worker": {"name":"홍길동","vfId":"VF1234"}, "photoBase64": "..." }
응답: { success: true }
```

**processReturnVendor**
```
요청: { "action": "processReturnVendor", "iprBarcode": "...", "worker": {...} }
응답: { success: true }
```

**processReturnParcel**
```
요청: { "action": "processReturnParcel", "iprBarcode": "...", "trackingNo": "...", "worker": {...} }
응답: { success: true }
```

모든 처리 API는 내부적으로 (1) `회송리스트`에서 F열 매칭 행 탐색 → 중복이면 실패 응답 → (2) S/T(/W)열 기입 → (3) `log` 시트에 한 줄 추가를 수행한다.

## 7. 로컬 검증 방법 (v1.0과 동일)

1. **Mock 모드**: `frontend/js/api.js`의 `MOCK_MODE` 플래그로 인메모리 가짜 응답 사용, 백엔드 없이 UI/스캔 흐름 확인.
2. **테스트 스프레드시트 연동**: `회송리스트`(3장 컬럼 구조) + `log`(빈 시트, 앱이 헤더 자동 생성) 두 탭을 가진 테스트 시트에 Apps Script 컨테이너 바인딩 → 웹 앱 배포 → URL을 `API_BASE_URL`에 설정. 단계별 가이드는 `docs/로컬-테스트-가이드.md`.

## 8. 이번 범위에서 제외하는 것

- 오프라인 큐잉/재시도 — 리스크로만 문서화
- 다중 센터 확장 대비 서버 전환 — 로드맵 이후 단계
- 상품바코드 기반 검색/매칭 — 미구현(표시 전용)
- 매칭행(h)/매칭구분/중복·재신고 점검 등 기존 시트의 QA용 보조 열 — 앱이 읽거나 쓰지 않음
