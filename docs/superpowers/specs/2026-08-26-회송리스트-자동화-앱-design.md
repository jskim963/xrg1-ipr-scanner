# 회송리스트 자동화 앱 — 설계 (v2.0)

작성일: 2026-08-26
근거 문서: `구현방안_회송리스트자동화앱.md`(v0.1 draft), `design_mockup.html`(UI 색상/스타일 레퍼런스), 실제 스프레드시트(`XRG1 회송리스트`) 구조 확인, 센터 현장 의견 및 사용자 확인 답변(본 대화)

v1.0 대비 변경: 센터 현장 피드백을 반영해 **작업 흐름을 스캔 우선(조회 → 작업 선택) 방식으로 전면 변경**하고, 실제 스프레드시트 컬럼 구조에 맞춰 데이터 모델과 API를 다시 확정했다. 차량 정보 입력을 폐기·회송 모두에서 제거했다.

## 1. 확정된 결정 사항

### 1-1. 작업 흐름 (센터 피드백 반영, v0.1에서 전면 변경)

- 기존(v0.1): 홈에서 [폐기]/[회송]/[조회] 중 하나를 먼저 선택 → 각 화면에서 다건 스캔 → 리스트 일괄 완료
- **변경(확정)**: 스캔이 곧 시작점이다. 다건 리스트 누적 방식은 사용하지 않고, **건별로 스캔→조회→처리를 완결**한다.
  1. 로그인 후 곧바로 스캔 대기 화면(=조회 화면 겸 홈)에 진입한다.
  2. IPR바코드를 스캔하면 즉시 조회 결과 카드(상품바코드, 오류신고일, 벤더명, 수량, 회수구분, D+6초과여부)와 함께 **[폐기 처리]/[회송 처리]** 버튼이 표시된다.
  3. **[회송 처리]** 선택 시 "회송 방식 선택" 화면에서 [업체직접회수]/[택배]를 **작업자가 직접 선택**한다. (v2.1에서 변경 — 최초에는 조회 결과의 회수구분(M열) 값으로 자동 분기했으나, 현장 피드백에 따라 수동 선택으로 바꿨다. M열 값은 여전히 조회 카드에 참고용으로 표시된다.)
  4. 각 처리(폐기/업체회송/택배회송)는 해당 건 하나에 대해서만 진행하고, 완료되면 **다시 스캔 대기 화면으로 복귀**한다. 다음 상품은 새로 스캔해서 동일한 사이클을 반복한다.
  5. 폐기 처리에서 "폐기존 이동 후 사진"은 **건별로, 폐기 처리 확정 후(현장에서 실제로 폐기존으로 이동한 뒤) 촬영**한다. 촬영 후 처리가 최종 완료되고 스캔 대기 화면으로 돌아간다.
- 이 변경으로 v0.1에 있던 "스캔 리스트 누적 + 개별 삭제" UI는 필요 없어진다.

### 1-2. 항목 변경 (센터 피드백)

- 폐기 처리: 차량번호/접안시간/발차시간 입력 **삭제**. '폐기차량 사진' → **'폐기존 이동 후 사진'** 으로 명칭 변경, 건별·처리 후 촬영으로 시점 변경(1-1 참고).
- 회송 처리(업체·택배 공통): 차량 정보 입력 **삭제**(도크에서 별도 취합).

### 1-3. 중복 IPR바코드 처리

F열(IPR)은 원칙적으로 유일해야 하는 값이다. `inquiry` 조회 시 F열에서 동일 값이 2행 이상 매칭되면 처리를 진행하지 않고 **"중복 IPR바코드 감지"** 경고를 표시하고 처리 화면으로 진입시키지 않는다(어느 행을 대상으로 할지 앱이 임의로 판단하지 않음).

### 1-4. 이미 처리된 건 재처리 방지

조회 시 T열(최종 처리)에 이미 값이 있으면 "이미 처리된 건입니다"를 함께 표시한다. 재처리 자체를 막지는 않되(현장 정정 필요 상황 대비), 경고 후 작업자가 계속 진행할지 확인하게 한다.

## 2. 아키텍처 (v1.0과 동일, 변경 없음)

- **프론트엔드**: PWA 단일 코드베이스 (Vanilla JS, 빌드 도구 없음). `design_mockup.html`의 색상 토큰·스타일을 재사용하되 화면 구조는 2-1의 새 흐름에 맞게 다시 구성한다.
- **바코드 스캔**: 카메라는 `BarcodeDetector` 우선 + `ZXing-js` 폴백. PDA는 포커스 유지 입력창 + `input`/Enter(`keydown`) 감지(XRG1 IPR 스캐너 HID 모드 지원 확인됨).
- **백엔드**: Google Apps Script `doPost(e)`, `Content-Type: text/plain;charset=utf-8` + `JSON.parse(e.postData.contents)`.
- **인증**: 서버측 토큰 검증 없음. 로그인 입력(작업자명, VF ID)은 클라이언트에 세션 보관 후 매 처리 요청에 `worker`로 동봉.
- **사진**: 클라이언트에서 리사이즈(긴 변 1280px) 후 base64 전송, `DriveApp` 저장 후 URL을 로그 시트에 기록.
- **일반 Gmail 계정** 기준 Apps Script 할당량(URL Fetch 20,000회/일, 트리거 90분/일) 적용 — 단일 센터 규모에서는 충분.

## 4. 화면 구성

1. **로그인**: 작업자명 · VF ID 입력 → [시작하기]
2. **스캔 대기(홈 겸 조회)**: IPR바코드 스캔 대기 상태. 스캔 시 `inquiry` 호출 →
   - 미등록: "미등록 IPR바코드" 안내, 계속 스캔 대기
   - 중복 매칭: "중복 IPR바코드 감지" 안내, 처리 화면 진입 차단
   - 정상: 결과 카드(상품바코드/상품명/오류신고일/벤더명/수량/회수구분/D+6초과여부, 이미 처리됨이면 경고 배지) + [폐기 처리]/[회송 처리] 버튼
3. **폐기 처리**: [폐기 처리] 선택 → "폐기존 이동 후 사진" 촬영 화면 → 촬영 완료 시 `processDiscard` 호출(해당 IPR 1건) → 완료 토스트 → 스캔 대기로 복귀
4. **회송 처리**: [회송 처리] 선택 → "회송 방식 선택" 화면([업체직접회수]/[택배] 버튼, 작업자가 직접 선택 — v2.1에서 M열 자동 분기 대신 수동 선택으로 변경)
   - 업체직접회수: 처리 확인 화면(요약 표시 + [처리 완료]) → `processReturnVendor` 호출 → 스캔 대기로 복귀
   - 택배: "운송장번호 스캔" 화면 → 스캔 시 `processReturnParcel` 호출(IPR+운송장 1쌍) → 스캔 대기로 복귀

상단 'XRG1 IPR 스캐너' 타이틀, 우측 상단 홈/로그아웃, 하단 '롯데글로벌로지스' 워터마크는 기존과 동일하게 유지한다. `design_mockup.html`의 색상 토큰(Lotte Red/Navy/Paper, 폐기=Amber, 회송=Blue, 조회=Teal)과 "IPR SCAN LOG" 스캐너 LCD 스타일 패널을 그대로 재사용한다.

## 5. API (Apps Script `doPost`, action 기반 라우팅)

모든 처리 액션은 **건당 1회 호출**(배열 대신 단일 IPR바코드). `token` 필드 없음.

**inquiry** — 스캔 시마다 호출(구 v0.1의 `iprBarcodeLookup`+`inquiry` 통합)
```
요청: { "action": "inquiry", "iprBarcode": "IPR2308050112" }
응답: {
  success: true,
  found: true,
  duplicate: false,
  alreadyProcessed: false,
  iprBarcode, productBarcode, productName,
  reportDate,      // A열
  vendor,          // H열
  qty,             // K열
  method,          // M열: "택배" | "업체직접회수"
  isOverDPlus6,    // R열 값 그대로
  existingStatus   // T열에 값이 있으면 그 값(alreadyProcessed=true일 때)
}
```

**processDiscard**
```
요청: { "action": "processDiscard", "iprBarcode": "...", "worker": {"name":"홍길동","vfId":"VF1234"}, "photoBase64": "..." }
응답: { success: true }
```

**processReturnVendor**
```
요청: { "action": "processReturnVendor", "iprBarcode": "...", "worker": {...} }
응답: { success: true }
```

**processReturnParcel**
```
요청: { "action": "processReturnParcel", "iprBarcode": "...", "trackingNo": "...", "worker": {...} }
응답: { success: true }
```

모든 처리 API는 내부적으로 (1) `회송리스트`에서 F열 매칭 행 탐색 → 중복이면 실패 응답 → (2) S/T(/W)열 기입 → (3) `log` 시트에 한 줄 추가를 수행한다.

## 9. 오프라인 지원 (v3.0, 신규)

인터넷이 안 되는 구역에서 최대 12시간(한 근무 교대) 동안 PDA/휴대폰이 로컬 데이터만으로 조회·처리를 계속할 수 있어야 한다는 현장 요구를 반영한다.

### 9-1. 동작 방식

1. **다운로드(동기화 내려받기)**: 로그인 직후(온라인 상태 가정) `syncDown` 호출 → **미처리 건만**(T열이 비어있는 행) 기기에 저장. 실제 운영 데이터 전체를 기기에 남기지 않기 위해 처리 완료된 행은 애초에 내려받지 않는다. 스캔 화면에서 [데이터 새로고침] 버튼으로 언제든 재다운로드 가능(온라인일 때만 의미 있음).
2. **오프라인 조회**: 네트워크 조회가 실패하면(또는 `navigator.onLine`이 false면) 로컬에 저장된 미처리 목록에서 IPR바코드를 찾는다.
   - 로컬에서 찾으면: 평소와 동일한 조회 카드 표시.
   - 로컬에서도 못 찾으면: "미등록 IPR바코드"가 아니라 **"재확인 필요(오프라인 상태 — 온라인 연결 후 다시 확인해주세요)"** 로 표시한다. 오프라인 스냅샷은 일부(미처리 건)만 들고 있으므로, 없다고 해서 실제로 미등록이라 단정할 수 없기 때문이다.
   - 이미 이 기기에서 오프라인으로 처리해 둔 건을 다시 스캔하면 "이미 처리된 건입니다(동기화 대기 중)"로 표시한다.
3. **오프라인 처리**: 폐기/회송 처리 완료 버튼을 눌렀을 때 네트워크 요청이 실패하면, 처리 내용(액션 종류, IPR바코드, 작업자 정보, 폐기 사진, 운송장번호, 처리 시각)을 기기에 큐로 저장하고 평소와 동일하게 "처리 완료" 화면으로 넘어간다(작업자 입장에서는 즉시 완료된 것처럼 보인다).
4. **업로드(동기화 올리기)**: 연결이 복귀했을 때(휴게시간, 작업 종료 후 등) 스캔 화면의 [지금 동기화] 버튼으로 큐에 쌓인 처리 건을 서버에 일괄 전송(`syncUp`). 서버는 건별로 순서대로 적용한다.

### 9-2. 동시 처리 충돌 규칙

여러 기기가 각자 오프라인으로 작업하다가, 같은 IPR바코드를 서로 다른 기기가 각자 처리한 뒤 나중에 둘 다 동기화를 시도하는 경우:

- **먼저 서버에 반영된 값(S열/T열/W열)이 유지된다.** 나중에 도착한 동기화 요청은 S/T/W열을 덮어쓰지 않는다.
- 나중 요청은 **AC열("중복/재신고 점검")에 "중복스캔" 문구를 추가**해 담당자가 눈으로 확인할 수 있게 한다(기존 내용이 있으면 덮어쓰지 않고 뒤에 이어붙인다).
- `log` 시트에도 "중복스캔으로 값 유지되지 않음" 비고와 함께 기록해, 어느 기기가 이 시도를 했는지 남긴다.
- 기기 분실 시 로컬에 남는 실제 운영 데이터(벤더명·연락처 등, 미처리 건에 한함) 유출 가능성은 현장에서 감수 가능하다고 확인되어 별도 보호 조치(암호화 등)는 하지 않는다.

### 9-3. API 추가

**syncDown** — 미처리 건 스냅샷 다운로드
```
요청: { "action": "syncDown" }
응답: { success: true, items: [ { iprBarcode, productBarcode, productName, reportDate, vendor, qty, method, isOverDPlus6 }, ... ] }
```
(반환되는 건은 정의상 전부 미처리 상태이므로 `alreadyProcessed`/`existingStatus`/`duplicate` 필드는 내려주지 않는다.)

**syncUp** — 오프라인 처리 큐 일괄 업로드
```
요청: {
  "action": "syncUp",
  "items": [
    { "action": "processDiscard" | "processReturnVendor" | "processReturnParcel",
      "iprBarcode": "...", "worker": {...}, "photoBase64": "...", "trackingNo": "...",
      "offlineTimestamp": "2026-08-27T09:12:00.000Z" }
  ]
}
응답: { success: true, results: [ { iprBarcode, status: "applied" | "duplicate" | "not_found" }, ... ] }
```
`applySyncItem_`는 각 건에 대해 (1) IPR 매칭 → 못 찾으면 `not_found`, (2) 이미 T열이 채워져 있으면 `duplicate`(AC열에 "중복스캔" 추가, S/T/W 미변경), (3) 아니면 평소 처리 핸들러와 동일하게 `offlineTimestamp`를 처리 시각으로 사용해 S/T(/W) 기입 + `log` 추가 후 `applied`.

## 10. 오입력 방지 및 조회 화면 개선 (v3.1, 신규)

현장 사용 중 실제로 겪은 오입력 우려와 화면 가독성 요청을 반영한다.

### 10-1. 처리 화면 뒤로가기

폐기/회송 처리 화면에 진입한 뒤 잘못 선택했음을 알아챈 경우, 처음부터 다시 스캔하지 않고 **바로 이전 화면으로 돌아갈 수 있어야** 한다.

- 폐기존 이동 후 사진 화면, 회송 방식 선택 화면의 [뒤로가기] → 스캔 대기 화면으로 돌아가되, **조회 결과(inquiry)는 지우지 않는다** — 방금 조회했던 카드가 그대로 다시 보이고 [폐기 처리]/[회송 처리] 버튼도 다시 뜬다(재스캔 불필요).
- 업체직접회수 처리 화면(10-4), 택배 회송 스캔 화면의 [뒤로가기] → 회송 방식 선택 화면으로 돌아간다(조회 결과는 유지).
- 기존 [취소] 버튼을 전부 [뒤로가기]로 대체한다. "스캔 대기 화면으로 완전히 초기화"하는 기존 [취소]의 동작(조회 결과까지 지움)은 더 이상 쓰지 않는다.

### 10-2. 조회 카드에 IPR바코드 표시

조회 결과 카드 맨 위(상품바코드보다 위)에 방금 스캔한 IPR바코드 값을 그대로 표시한다. 스캔값과 화면에 뜬 정보가 같은 건인지 작업자가 바로 확인할 수 있게 하기 위함이다.

### 10-3. 상품바코드 뒷 4자리 강조 표시

조회 카드의 상품바코드 값 중 **맨 뒤 4자리를 시각적으로 강조**(굵게+포인트 컬러)해서, 바코드가 길어 한눈에 안 들어오는 문제를 줄인다. 4자리 이하인 값은 전체를 강조한다.

### 10-4. 업체직접회수 2단계 분기 + 재확인

업체직접회수를 선택하면 곧바로 처리 완료로 넘어가지 않고, **"업체직접회수 처리" 화면에서 [회송존 이동] / [회수 완료] 중 하나를 고른다.** 실제 현장 흐름(회송존으로 먼저 옮겨두었다가, 나중에 업체 트럭이 와서 수거)을 반영한 것이다. 두 갈래는 서로 독립적인 선택지이며(선후관계를 강제하지 않음), 둘 다 오입력 방지를 위해 **선택 즉시 처리하지 않고 재확인 창(네이티브 confirm)을 띄운 뒤 확인해야 실제로 처리된다.**

- **[회송존 이동]** 선택 → 재확인 → 확인 시 `processReturnZoneMove` 호출 → **U열에 처리일, V열에 `'회송존 이동'` 문자열**을 기입한다. **S/T열(최종 처리)은 건드리지 않는다** — 아직 최종 처리가 아니라 중간 상태이기 때문이다. 이후 이 건을 다시 스캔하면 여전히 "미처리" 건으로 조회된다(회수 완료 처리를 나중에 별도로 할 수 있도록).
- **[회수 완료]** 선택 → 재확인 → 확인 시 **기존과 동일하게** `processReturnVendor` 호출 → S열/T열에 기입(`T열 = '업체 트럭 회송'`, 변경 없음).
- 두 액션 모두 오프라인 지원 대상이다(9장의 온라인 우선 시도 → 실패 시 큐잉 규칙을 동일하게 따름).

### 10-5. API 추가

**processReturnZoneMove**
```
요청: { "action": "processReturnZoneMove", "iprBarcode": "...", "worker": {...} }
응답: { success: true }
```
내부적으로 (1) F열 매칭 행 탐색 → 못 찾거나 중복이면 실패 응답, (2) U열=처리일, X열=`'회송존 이동'` 기입, (3) `log` 시트에 처리구분 `'회송존 이동'`으로 한 줄 추가를 수행한다. `syncUp`의 `applySyncItem_`도 `item.action === 'processReturnZoneMove'`를 동일한 방식으로 처리하도록 확장한다(단, 이미 최종 처리(T열)된 건이면 다른 액션과 동일하게 `duplicate` 처리 후 AC열에 "중복스캔"을 남기고 U/X는 건드리지 않는다).
